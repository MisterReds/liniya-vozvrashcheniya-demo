# 14. Архитектура собственного 2D-движка

Статус: технический эскиз и границы engine spike. Собственный движок запрошен пользователем; предложенный язык — C++20, SDL3 — платформенный слой, первая платформа — Windows PC.

## Граница «своего движка»

Мы пишем собственную игровую runtime-систему и не используем готовый игровой движок или ECS-фреймворк. SDL3 — библиотека платформенного слоя: создаёт окно, сообщает события ввода, предоставляет таймеры и открывает аудиоустройства. На первом этапе SDL также презентует готовый буфер кадра в окно, но не строит игровую сцену.

С нашей стороны остаются игровой цикл, фиксированный шаг симуляции, пиксельный framebuffer, отрисовка тайлов/спрайтов/UI, камера, загрузка и проигрывание покадровой анимации, карта уровня, простые коллизии, состояния жителей/врагов, взаимодействие, ресурсы и формат сохранения.

Мы не пишем собственную операционную систему, оконный менеджер, драйвер видеокарты, компилятор шейдеров, 3D-движок, редактор универсальных сцен или платформенные SDK консолей. Такой объём не улучшит первый playable и отдалит работу над игрой.

## Минимальная архитектура

```text
SDL3 Platform
  ├── окно, события, таймер, клавиатура/мышь/геймпад
  └── вывод буфера кадра и звуковой поток
       ↓ узкий интерфейс Platform
Наш Runtime
  ├── App / fixed-step loop / время и пауза
  ├── InputMap: физические устройства → игровые действия
  ├── PixelRenderer: framebuffer, clipping, sprite/tile blit, UI primitives
  ├── AssetStore: PNG/описание спрайта/анимация/карта
  ├── Scene: enter/update/draw/leave
  ├── World: сущности, компоненты, AABB-столкновения
  └── SaveStore: версия формата, сериализация состояния
       ↓ использует Runtime, но не SDL
Игра
  ├── StationScene
  ├── Player / Survivors / Threats
  ├── DayNight / Resources / Buildings
  └── UI и правила победы/поражения
```

## Первые технические решения

- **Язык:** C++20. В коде отделять платформенные вызовы от игровых систем; не передавать `SDL_Event` в правила игры.
- **Сборка:** CMake; зависимости фиксировать по версии. SDL3 подключается как внешняя библиотека.
- **Целевая сетка:** проверить внутренние 640×360 и 16×16 тайл на тестовой сцене. Выбрать окончательно после просмотра масштаба персонажа, UI и объёма уровня.
- **Рендеринг:** собственный CPU буфер RGBA8 в низком разрешении; прямоугольники, blit прямоугольника спрайт-листа и простая сортировка по Y. SDL3 показывает буфер с nearest-neighbour масштабированием. Внутренний renderer остаётся заменяемым.
- **Симуляция:** фиксированный шаг 60 Гц; отрисовка не управляет временем мира.
- **Карта v0:** текстовый формат тайловых слоёв с отдельно заданными объектами/точками интеракции. Не создавать собственный визуальный редактор, пока карты можно быстро править и проверять другим способом.
- **Персонажи:** спрайт-лист с метаданными кадров/анимаций; idle, walk, work, attack, hurt. Pivot и коллизия задаются в данных.
- **InputMap:** действия `move_left`, `move_right`, `interact`, `attack`, `pause`; конкретные клавиши и кнопки — отдельные привязки.
- **Данные игры:** состояния объектов и параметры баланса хранятся в человекочитаемых данных, чтобы не перекомпилировать код при настройке значений.

## Репозиторий после первого playable

```text
engine/
  CMakeLists.txt
  include/engine/{App,Input,Scene,PixelRenderer,AssetStore}.hpp
  src/{platform/sdl3,core,render,assets,world}/...
game/
  include/game/...
  src/{scenes,actors,systems,ui}/...
assets/
  source/                 # исходники LibreSprite/Aseprite, звук
  runtime/                # экспортированные тайлсеты, карты, метаданные
docs/
tools/                    # валидаторы/конвертеры, когда подтвердится потребность
```

Прототип браузера остаётся в своей папке/ветке как одноразовый тест идеи. Его DOM и Canvas код не становится зависимостью C++-движка.

## Порядок реализации движка

1. Окно, цикл приложения, закрытие, resize и отладочный лог.
2. Пиксельный буфер, очистка, прямоугольник, вывод кадра без размытия.
3. InputMap для клавиатуры/мыши и геймпада; движение квадратного тестового персонажа.
4. Камера, тестовая tilemap, слои, спрайт-лист и walk-анимация.
5. Коллизии, простые сущности и загрузка сцены.
6. Сбор ресурсов, интерактивные объекты и состояние жителей.
7. День/ночь, атака, проигрыш/победа.
8. Сохранение, audio bus, меню, настройки и автономная Windows-сборка.

Каждый этап должен оставлять рабочую сборку. Если собственная система не нужна для этой игры, она не попадает в движок.

## Definition of done для engine spike

- Чистая Windows-сборка открывает окно 16:9 и корректно закрывается.
- Кадр рисуется нашим pixel renderer и увеличивается целыми коэффициентами без bilinear blur.
- Клавиатура и геймпад управляют тестовым персонажем через InputMap.
- Tilemap и walk-анимация загружаются из внешних файлов.
- Детерминированное обновление не зависит от случайного FPS; пауза останавливает симуляцию.
- В GitHub Actions можно воспроизвести сборку по зафиксированным версиям.

Пока spike не готов, большую игру и объёмный арт не производить. Сам движок не является целью релиза; он должен достаточно быстро дать нужный игровой цикл.

## Состояние каркаса

В каталоге `engine/` уже создан и собран первый прототип runtime: SDL окно/события, fixed-step loop 60 Гц, собственный программный pixel framebuffer 640×360, камера, повторяемый слой земли и тестовые сущности. В игре реализованы стартовый экран, движение, сбор лома/топлива, работа жителя-сборщика, ремонт генератора, баррикада, ночные волны, атака, победа/поражение и повтор. Каркас принимает клавиатурный ввод и обнаруживает геймпад.

Нативная CMake-сборка и однокадровый SDL dummy/offscreen запуск прошли в Linux-среде. WebAssembly-версия этого же C++ кода запущена в Chromium; полный цикл до победы пройден на браузерной сборке, мобильное касание проверено. Интерактивное окно на реальном рабочем столе и Windows сборка пока не проверены. Tilemap-файлы, загрузчик спрайтов, сцены в отдельных модулях и игровой звук ещё предстоит добавить. `engine/src/main.cpp` пока собирает первый вертикальный срез в одном файле; разделять модули будем после фиксации механик.
